# Rivet record workflow

The October validation call changes the default workflow to a PM-owned comment and change record for custom and first-time equipment orders. It does not depend on the electrical attribute registry or the Larkspur fixture. The previous engineering engine remains available in code/API for later stages; it is no longer the default dashboard.

## Persistence and authority

- `OrderRecord` owns an independent version and durable JSON record: comments, changes, subscribers, notice drafts, approvals, and before/after edit events. Originals remain immutable `Document` blobs and `Span` citations. Migration `0004` adds the records without replacing existing orders.
- A durable parse worker imports numbered comments and PDF annotation objects. Unknown author/date/location remain explicitly unconfirmed. An unstructured email becomes one reviewable row, not invented separate issues. No AI-generated fix, response, or compliance determination is applied.
- `original_text` remains immutable when a PM corrects `text`. Every write requires a reason, optimistic version, and idempotency key. In authenticated workspaces the server records the verified user ID rather than trusting a submitted actor name. Local development keeps named actors. Target drawing citations and email links must belong to the same order.
- Source-page and target-location are separate fields. All imported rows need PM review. Confidence is qualitative (`Needs review` / `PM reviewed`), never a fabricated model probability.
- Open/responded/closed are explicit communication statuses. Responded/closed require a response and its author; closed also requires review. Coordination can prepare a proposed next step, but a new source never silently proves an engineering fix or discards older rounds.
- Changes are human-confirmed records with from/to values, revision labels, linked comments, requester, and recorded approval. Deterministic text comparison provides source-linked candidates; geometry and scanned content are not interpreted.

## Approvals and shared records

A record approval freezes the comments, responses, changes, and source references, even when some comments remain open. It certifies a reviewed record, not equipment compliance or production release. Later edits remain in the working version. Read-only links contain a random token; only its SHA-256 hash is persisted. Each expires after 30 days and can be revoked. The projection excludes subscribers, internal edit events, and unrelated inbox sources. Referenced original documents are included in full, with token-scoped download checks, except for email: shared EML downloads contain only the frozen approved source excerpts. Raw MIME headers, private recipients, and embedded attachments are never included through that shared email route. Authenticated workspace users retain access to the original EML.

The running development app retains its localhost boundary. Clerk authenticates workspace requests; each database query and write uses the verified active organization. Public record links authorize only their frozen snapshot and included source documents. A link on localhost still works only on this computer. Hosting and production Clerk/domain setup remain separate. See [accounts and email setup](accounts-email-setup.md).

## Email and notice boundary

`POST /api/orders/{id}/record/email` accepts a saved `.eml`, preserves its headers/body and imports supported attachments through the existing document queue. Byte-identical messages are deduplicated within an order. Unsupported attachments produce an explicit error. The same intake service handles Resend deliveries. A configured receiving domain enables random per-order addresses. Verified webhook events queue durable work; the worker rechecks the envelope recipient, downloads the original MIME email, and imports supported attachments. Unsupported attachments in forwarded messages remain in the immutable original and are listed in metadata.

Recipients are grouped as Manufacturer, Customer, or Production. Comment changes, new intake, recorded changes, and approvals append a durable notice draft with a recipient snapshot. `.eml` drafts have `X-Unsent: 1` and can be reviewed and sent from an email app. After a verified sender is configured, a user can explicitly review and send a notice. A durable delivery record freezes recipients and content, and per-recipient Resend idempotency keys prevent duplicate sends inside the provider retry window. Provider acceptance is recorded as sent; inbox delivery is not inferred. No notice is sent automatically.

If recipients are added after a draft was prepared, **Use current recipients** explicitly updates that unsent draft's snapshot and records the old and new lists. The action validates recipients against the same order and refuses changes once any delivery has been queued, including failed deliveries. Updating recipients creates no delivery job; sending remains separate.

## Rivet questions

`POST /api/orders/{id}/record/ask` answers from a bounded snapshot of this order. The model receives read-only context, a strict answer schema, and no mutation tools. References outside the supplied source/comment/change sets are rejected. The Rivet inspector opens with its toolbar button or Cmd/Ctrl+J and shows the conversation, record version used for each answer, and clickable citations. Migration `0008` saves validated questions and answers on the server, scoped to the organization, order and individual user; reloading or navigating away does not erase them. The server supplies recent history rather than trusting client-supplied messages. An idempotency key prevents duplicate submissions. Questions do not modify the order record. Actual notice-delivery state is separate from prepared drafts in the answer context.

`OPENAI_API_KEY` and `OPENAI_MODEL` remain server-only. Without them the record workflow remains usable and questions return a clear connection error. The assistant does not draft fixes, close comments, approve records, or send notices.

## Interface and validation

`RecordFeed` separates the cross-order Work inbox from the Orders list. `/api/records/inbox` projects actual reviewable comments, assignments, active or paused runs, and current proposals; it does not invent customer-waiting states. Entries deep-link to their source comment, task or proposal. `RecordWorkspace` opens in Review work, followed by Comment log, Sources, Changes and Sharing. The workbench places the original document beside one Record/Rivet inspector, with a collapsible review queue and a separate Team tasks control for owners, due dates and readiness. Source citations preserve the document view while the inspector switches between the record, persistent agent tasks, private questions and activity. Narrow screens stack the source and inspector without horizontal overflow. `SharedRecord` remains a separate read-only projection. The homepage workbench preview is explicitly illustrative and does not modify customer records.

Run `uv run pytest tests/test_records.py -q` against the dedicated `rivet_test` database. Tests cover a non-electrical custom order, persistence across rounds, original text and edits, stale writes, source isolation, status gates, immutable approval links, revocation, EML attachments/deduplication, notice drafts, Excel exports, and document comparisons. Existing engineering tests remain regression coverage for retained functionality.

Public-source regression coverage and known extraction limits are recorded in [public-document-validation.md](public-document-validation.md). Uploads reject PDFs exceeding 150 pages or files exceeding 20 MB before persisting an unusable document.

## Explicit record relationships

`backend/records/connections.py` derives a deterministic relationship index from persisted IDs: comment → source document/annotation, drawing area, imported email, change, edit event, and the latest approval snapshot. Coordination extends this with exact anchors and records why a drawing was linked. A unique, corroborated equipment-tag and sheet match can be linked internally; ambiguous candidates require a person to choose. The original markup location and the referenced drawing remain separate. Neither an automatic link nor a PM-selected location proves that the issue is resolved.

The UI uses this index for source links, reciprocal comment/change navigation, and focused history. The assistant receives the same bounded relationships with the record context. An approval comparison checks saved content against the frozen snapshot; a later response, change, or new document is surfaced as an update after record approval. This does not imply production has begun, a design has been approved, or a customer has been informed. Recipient setup is visible, while notice drafts remain unsent until a person explicitly sends them.

Review next and Save & next advance through pending reviews without checking the review box for the user. PDF zoom and publisher page mapping make verification easier. The real-data regression walks all 13 public annotations through review, recorded response, a linked test change, record approval, Excel/PDF exports, and a frozen shared snapshot; a subsequent edit changes the working record only.

## Connected coordination

The coordination state belongs to the order's versioned record. It includes extracted anchors, typed relationships, suggestions, role assignments, activity, readiness checks, due dates, and acceptance counts. Every suggestion retains its reason and source IDs. Resolution uses the same optimistic version, tenant scope and idempotency boundary as record edits. The assistant can explain this state with citations, but has no mutation tools.

Exact references are evidence of a relationship, not an engineering judgment. Conflicting or incomplete references stay reviewable. A comment with no usable anchor gets a clarification draft. An accepted draft remains a draft; external delivery requires the separate, explicit notice send action. Email threads use preserved message headers rather than a matching subject alone.

Internal automated work appears in activity. Undo is guarded by the current affected values so it cannot overwrite later human edits. Skips, corrections and edited acceptances are retained. Acceptance counts are measurements, not a claim of model confidence; no percentage automatically grants more permissions.

Role routing creates coordination work for the PM, drafting, production or commercial team. An assignment does not mean the engineer completed it. Resubmittal and release checks expose missing communication and review evidence. They do not certify title-block stamps, geometric drawing changes, compliance, customer approval or physical readiness for manufacture. The approved record remains a frozen communication snapshot.

Background coordination checks create due-date reminders and weekly summary drafts when enabled. They never send mail themselves. The default scope remains one order with its explicitly uploaded/forwarded documents. SharePoint, network-drive synchronization, CAD writes, automatic technical closure, cross-customer learning and unsupervised outbound mail remain future integrations; none are represented as connected.

Use [the connected-review fixture](../examples/connected-review/README.md) to reproduce clear, ambiguous and missing-reference cases with ordinary ingestion. It complements, rather than replaces, the real public-PDF regression. Production topology and the remaining live-host checks are documented in [deployment](deployment.md).

## Durable order agents (v2)

Migration `0007` adds `RecordAgentRun` and `RecordAgentProposal`. These are independent of the retained quote agent: the order agent can prepare coordination work but has no pricing, approval, comment-closure, engineering-response, CAD-write, arbitrary SQL, or outbound-send tool.

`POST /api/orders/{id}/record/agent/runs` creates a saved goal against an exact record version. The existing PostgreSQL job worker claims the run under a tenant identity. Actual tool calls, outputs, evidence IDs, usage, failures and human answers are checkpoints. Reloading the browser does not stop work or erase it. Run state progresses through `queued`, `running`, `waiting_for_input`, `waiting_for_review`, `completed`, `failed`, or `cancelled`. Resume and retry create a new generation; job payloads and late provider responses are fenced by that generation as well as the worker lease. A cancelled older job cannot continue a newer retry.

The Responses tool loop defaults to `gpt-6-luna` with low reasoning effort. `RIVET_AGENT_MODEL` may select another server-configured model; Astra is explicitly refused. The API key remains server-only. No key means a visibly labeled **rule-based** inspection that prepares source-reference clarification drafts, with no claim that an AI model ran. AI calls use strict typed tools, a per-call output limit, a maximum number of calls, bounded context and a per-generation token allowance. Actual input/output usage is retained; no dollar-price estimate is fabricated. Provider failures retain saved work and never silently become a successful AI run.

The loop persists actual Responses function-call/output pairs and opaque reasoning continuation in private run state with `store: false`; public activity contains tool observations, never reasoning payloads. Context trimming preserves complete call/output turns. Successful read arguments are cached within the current evidence checkpoint. A duplicate returns the saved observation without another completed-work entry, while its actual model usage still counts. The next call enters a bounded finalization phase that offers only staging, a specific missing-evidence question, or completion; after staging it offers completion only. A fully read inventory is removed from the available tools. If the provider still repeats a read, the run stops with retained work and an explicit retryable failure, not a generic planning question for the user. Search observations distinguish reviewer annotations from drawing text; finding only the comment itself cannot establish its drawing target. Retries and changed evidence clear this cache and protocol; an answer on unchanged evidence continues from the saved observations. This follows the [Responses function-calling protocol](https://developers.openai.com/api/docs/guides/function-calling) and [stateless reasoning continuation](https://developers.openai.com/api/docs/guides/reasoning).

Available tools read the record with pagination, read source anchors or paginated document spans, search extracted text, traverse direct typed relationships, compare two selected documents' extracted text, stage changes, ask a specific question, or finish. Model-proposed changes must cite source IDs that were actually returned by successful read/search tools. Source ownership is checked again by the server. Tool content, document instructions and playbook prose never grant new capabilities.

One change set consolidates a run's proposed source links, clarification drafts, internal tasks and summary drafts. The reviewer sees the operations, prior values, evidence and origin. Acceptance requires the current record version, unchanged source/record fingerprint and a human actor. It commits all operations atomically, records the originating run/proposal, and preserves originals. Source-link acceptance does not mark a comment reviewed or closed. Accepted drafts have no recipients and remain unsent. Already accepted exact operations are not re-staged on repeated runs. New evidence makes pending proposals stale; it does not modify frozen historical approvals.

Background runs require an explicit per-order opt-in in `agent_settings.enabled`; existing orders default to off. The separate `RIVET_AGENT_AUTORUN=false` deployment switch disables all event scheduling while leaving manual commands available. The worker scans enabled orders once per minute and deduplicates by evidence fingerprint. A changed input can resume a saved investigation waiting for an answer. Each playbook edit is versioned and recorded; the playbook is scoped to that order and cannot authorize sending or technical decisions. This is not automatic cross-customer learning.

`GET /api/orders/{id}/record/graph` projects typed source/document, comment, response, change, task, role, prepared communication, recorded-delivery, approval and proposal relationships. Equipment and sheet mentions remain explicitly unreviewed references. Source markup and drawing target are separate edges. A notice draft and a recorded sent delivery are different nodes; acknowledgment is not inferred. Recipient email addresses are not exposed through this graph. PostgreSQL remains the system of record; a separate graph database is not required.

The implementation deliberately starts with conservative whole-record proposal invalidation. Fine-grained dependency recomputation, confirmed document families, general bitemporal assertions, geometry/OCR review, reusable team-wide learned procedures, and autonomous external sending are **not implemented**. Text comparison is not proof of engineering resolution. The graph is an inspectable projection of recorded evidence, not a verified engineering model.

`tests/test_record_agent.py` covers durable rule and AI-tool runs, explicit human commit, idempotency, cross-order source rejection, forbidden tools, stale proposals, cancel/retry generation fencing, saved clarification continuation, automatic opt-in/deduplication, pagination, bounded model context, protocol replay/privacy, repeated-read protection and token/call accounting. Provider behavior is mocked in these tests; live-model quality and document extraction accuracy require separate evaluation.
